# Hub status
Maintains the shared status store of one project hub vault (an Obsidian vault that is a git repo shared by the whole project). Three modes: **todos**, **update**, **post-meeting**. Every write goes through the `hub` command; never edit files under `Status/` by hand. `hub <command> --help` documents every option.
## Before any mode
1. Work from the vault root (the directory with `project.yaml`). Check `hub.local.yaml` has `me: <your people key>`; if not, ask the user which key in `project.yaml` people is them and add it.
2. If the vault is not a git repository, stop and tell the user to set it up first (`hub-init`, a later plan). In a dry run, note it and continue without the git steps (pull, `hub commit`, `hub snapshot`). Otherwise run `git pull --rebase` (skip in a dry run). If it fails, stop and show the error. In post-meeting mode the workbook edited in the meeting (`Agenda/<series>.xlsx`) is an uncommitted change, so run `git pull --rebase --autostash` instead (`hub agenda read` then warns that it could not pull; that warning is expected there, since you just pulled). Record `git stash list` BEFORE the pull. After the pull, run `git stash list` and `git status --short`. STOP if the stash list gained an entry, or if any status line has a code containing `U`, or `AA` or `DD`: the meeting workbook edits may be sitting in the stash. Show the user, and do not run `hub agenda read`.
3. Run `hub validate` and note existing violations (do not fix unrelated ones silently).
4. Make a scratch directory **outside the vault**: `SCRATCH=$(mktemp -d)`. Every temporary file (tasks.json, batch files, proposal files) goes there, never inside the vault, because `hub commit` stages everything in the vault. Delete it at the end (`rm -rf "$SCRATCH"`).
5. **Dry run.** If the user says "dry run", run only this allow-list: `hub validate`, `hub list`, `hub show`, `hub since`, `hub seen`, `hub sources`, `hub pending list`, `hub clickup plan`, `hub meeting decided`, `hub sync-state get`, `hub ingest git` without `--advance`, and read-only connector calls (search, read, list, get). Everything else is a write and is skipped, in particular: `hub new|entry|set|link|log`, `hub ingest batch`, `hub clickup apply`, `hub pending add|apply|reject`, `hub agenda read|scaffold|build`, `hub snapshot`, `hub meeting next`, `hub sync-state set`, `hub commit` (including the per-source commits), editing `hub.local.yaml`, `git fetch`/`git pull`/fast-forwards, and connector write tools (ClickUp create/update). Write the batch files to the scratch directory and show them instead. ClickUp has no batch file: show the `hub clickup plan` JSON. For steps 6 to 8, describe what they would do with the proposals found, without simulating them. Tell the user which steps were skipped.
## Mode: todos
`hub list --type action --status open --owner me --json` (or `--owner <key>` for someone else). Sort by the `due` key (rows without one last), then by `priority`. Present a short list: title, id, due date, the decision it came from (`hub show <id> --chain` on request). Mention `hub pending list` if proposals are waiting for approval. No writes.
## Mode: update
1. `hub sources` lists what is configured and when each source was last ingested.
2. For each configured source, one at a time, follow its reference file in `sources/` (next to this file): ClickUp → `sources/clickup.md`, Circleback → `sources/circleback.md`, each repository and Overleaf → `sources/git.md`, calendar → `sources/calendar.md`, opted-in personal notes → `sources/notes.md`, Gmail/Slack → `sources/mail-chat.md`. Each ends with either `hub ingest batch <file>` or `hub clickup apply`. If `hub ingest batch` rejects the file, fix every listed problem and re-run; nothing was written.
3. **Pull before, commit after, each source.** Start each source with `git pull --rebase` (the tree is clean: the previous source was committed; in a dry run skip it). Right after a source's `hub ingest batch` (and its watermark step) or `hub clickup apply` + `hub sync-state set clickup`, run `hub commit "status: <source> (<YYYY-MM-DD>)"` (it pulls, then pushes). This way each source's `hub seen` checks and `hub clickup plan` run against everything other people pushed until minutes earlier, and what you wrote is pushed before you move on, which is what stops two people ingesting the same day from recording the same meeting, task or commit twice. Exit code 3 means a real conflict: stop, show the message, and do not resolve it by guessing.
4. Classify every fact with this table — the batch format enforces the left column, the right column always goes in `proposals`:

| Apply directly (`safe`) | Staged as a proposal |
|---|---|
| an entry on an existing item, with its source | closing a question (answered/dropped/pivoted) |
| a log line, with its source | recording a decision as made (except via `hub agenda read`) |
| a new open question raised, with its source | a pivot (question replaced by another) |
| mirroring ClickUp status/assignee/due onto linked actions (`hub clickup apply`) | new actions from a tracker or the agenda read-back: staged automatically by `hub clickup apply` / `hub agenda read` — approve them in the approval batch |
| | every action found in notes, Circleback, Gmail or Slack, even with a named owner |
| | any change to Vision.md or Knowledge/ |

5. Before writing anything derived from a source id, `hub seen <source>` — after this source's pull (step 3), never from an earlier check; skip what is already recorded unless it adds a new fact. An `unreadable:<path>` entry means a vault file is broken and the answer may be incomplete: report it to the user and do not treat it as "already ingested". If a log cannot be read, `hub seen` exits 1.
6. **Approval batch.** `git status --short` must print nothing here (every source was committed in step 3). `hub pending apply` pulls first, so its warning `could not pull before acting … unstaged changes` cannot appear after the per-source commits; if it does, something was left uncommitted: run `hub commit "status: <what> (<YYYY-MM-DD>)"` first, then continue. If proposals were staged, list them with `hub pending list`: for each, its proposer, and one line on what applying does. Before offering a `New ClickUp task: <name>` proposal, look for an open action with the same title (`hub list --type action --status open`, whitespace and case-insensitive). If there is one, it is the same task: link it with `hub set <A-id> clickup_id=<task id>` (the task id is in the proposal's `source`, `clickup:<task id>`) and reject the proposal instead of applying it. In the prompt, call out ClickUp tasks whose status is not done but not really active (e.g. "paused"; they become open actions) and proposals with no owner (after approval each needs `hub set <A-id> owner=<key>`). Ask the user once about the proposals staged in this run (apply all, apply some, or reject some); mention proposals staged by other people separately and leave them alone unless the user says otherwise. Then `hub pending apply <P-ids>` / `hub pending reject <P-ids>`.
7. **Close the gaps.** Run `hub validate` and fix every violation the applied proposals caused, one command each:
   - `decision-answers` (a made decision answers no question): find the question with `hub list --type question`, then `hub link <D-id> answers <Q-id>`. If no question exists, create it first: `hub new q "<the question the decision settles>" --series <series> --source <the decision's source>`, then link.
   - `decision-actions` (a made decision spawned no action and has no reason): ask the user what action follows from it and create it with `hub new a "<action>" --owner <key> --link spawned_by:<D-id> --source <the decision's source>`, or, if nothing needs doing, `hub set <D-id> no_action="<reason>"`.
   - `action-owner` or `unknown-owner` (an open action with no owner, or one not in `people`): ask the user who owns it, then `hub set <A-id> owner=<people key>`.
   - A `New ClickUp task` action applied without a decision: `hub link <A-id> spawned_by <D-id>` once the user names the decision it serves.
   Re-run `hub validate` until it reports only the violations noted before the run; report any you could not fix.
8. **ClickUp push.** If ClickUp is a source: re-run `hub clickup plan --tasks <file>` (the applied proposals may have created owned actions) and do the *Push* step of `sources/clickup.md` for the new `push` entries.
9. `hub snapshot`, then `hub commit "status: approvals and push (<YYYY-MM-DD>)"`. Exit code 3 means a real conflict: stop, show the message, and do not resolve it by guessing. Delete the scratch directory.
10. **Report** to the user: a table with one row per source — reached / not reachable (say why: connector missing, folder not shared, path not on this machine) / disabled / not configured — and what changed (entries, new items, flags, proposals applied or rejected), and the final `hub validate` count. Never present a partial run as complete.
## Mode: post-meeting
1. Identify the series and date (the user, or the series whose `Agenda/<series>.xlsx` has not been read back; ask if ambiguous).
2. `hub agenda read <series>` applies the decisions recorded in the workbook and stages free-text items. If it refuses, show its message (it explains what to do). Then `hub commit "status: agenda read-back <series> <date>"`.
3. **Circleback cross-check** (`sources/circleback.md`, section *Cross-check*): compare what was said with `hub meeting decided <series> <date> --json`; anything decided or assigned aloud but not recorded (neither in `decisions` with `reached: true` nor in the `staged` proposals) becomes a proposal. Commit it as in update step 3.
4. Run steps 1–5 of **update** for the other sources (ClickUp especially), committing each source, not a full update, so approvals happen once in step 5.
5. Then steps 6–10 of update, in that order: approval batch → close the gaps (`hub validate` ends with no new violations) → ClickUp push (new actions need tasks, including the ones from the proposals just applied) → snapshot and commit → report.
## Writing entries
One factual sentence each, with numbers when there are numbers ("4×3 open-boundary run finished: F = 0.97 at 1092 parameters"). Name the item the fact serves. Cite the source id in `--source` (formats in each source file).
## Privacy (the vault is read by everyone on the project)
Record decisions, stated positions ("Eun-Ah prefers framing B") and actions with their source. Never record personal assessments of people, career or 1:1 material, health, or anything from someone's private notes verbatim. Ignore private notes in Circleback results (`ReadMeetings` and `SearchMeetings`). When unsure whether something belongs, leave it out and mention it to the user.
